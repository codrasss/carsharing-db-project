# Каршеринг — учебный pet-проект по проектированию БД

Проект по проектированию и реализации реляционной базы данных в PostgreSQL: от концептуальной модели до готовой схемы с данными, аналитическими запросами, индексами, представлениями, процедурами и транзакциями.

## О проекте

**Предметная область:** сервис каршеринга (аренда самокатов, велосипедов и автомобилей). Пользователи регистрируются в приложении, берут транспорт на станциях, совершают поездки по одному из версионируемых тарифов, оплачивают поездки, могут применять промокоды. Транспорт периодически проходит техническое обслуживание.

**Состав схемы — 9 сущностей:**
- `users` — пользователи сервиса
- `stations` — станции парковки транспорта
- `vehicles` — транспортные средства (самокаты, велосипеды, автомобили)
- `tariffs` — тарифы (версионируемая таблица, SCD2 — см. обоснование ниже)
- `trips` — поездки (центральная факт-таблица)
- `payments` — платежи по поездкам
- `promocodes` — промокоды на скидку
- `trip_promocodes` — связка поездок и применённых промокодов (M:M)
- `vehicle_maintenance` — журнал технического обслуживания транспорта

**Нормализация:** схема приведена к 3НФ. Устранены повторяющиеся группы (1НФ — например, история обслуживания вынесена в отдельную таблицу вместо списка в одном поле), частичные зависимости от составного ключа (2НФ — проверено на `trip_promocodes`), транзитивные зависимости (3НФ — например, цена тарифа не хранится напрямую в `trips`, а достаётся через `tariff_key`).

**Версионирование (SCD2):** таблица `tariffs` реализует SCD2 — при изменении цены тарифа старая версия не перезаписывается, а закрывается (`valid_to`, `is_current = false`), и добавляется новая строка. Это позволяет каждой поездке навсегда ссылаться на ту версию тарифа, что действовала в момент поездки, не искажая финансовую историю задним числом. SCD1 не подходит, так как теряет историю полностью; SCD3 не подходит, так как хранит только одну предыдущую версию, а тариф может меняться многократно.

## Физ. модель

![Физическая модель](docs/physical-model.png)

Диаграмма построена по реальной структуре базы данных (сгенерирована в DBeaver из уже развёрнутой схемы) и показывает все 9 таблиц с полным набором столбцов, их типами данных и связями (первичные и внешние ключи) между таблицами.

Полное текстовое описание всех атрибутов, типов данных PostgreSQL и ограничений (PK, FK, UNIQUE, CHECK, DEFAULT) для каждой таблицы — см. [`docs/physical-model.md`](docs/physical-model.md).

Ключевые архитектурные решения:
- Суррогатные первичные ключи (`serial`) во всех таблицах, кроме `trip_promocodes`, где используется составной ключ `(trip_id, promocode_id)` — так как уникальность строки в этой таблице определяется именно парой значений
- `ON DELETE RESTRICT` на связях, где удаление родителя угрожает финансовой истории (пользователь, транспорт, тариф в поездках)
- `ON DELETE CASCADE` там, где дочерние записи бессмысленны без родителя (платежи, обслуживание, связка промокодов)
- `ON DELETE SET NULL` на связи `vehicles → stations`, где удаление станции не должно уничтожать запись о транспорте — оно просто "теряет" текущую локацию
- `CHECK`-ограничения на уровне БД для всех бизнес-правил (неотрицательные суммы, корректные координаты, допустимые статусы)

## Сценарии использования

### Скрипты

Все SQL-скрипты находятся в папке `scripts/`:

| Файл | Содержимое |
|---|---|
| `01_ddl.sql` | Создание всех 9 таблиц схемы (`CREATE TABLE`) с ограничениями |
| `02_dml.sql` | Заполнение таблиц данными (`INSERT`) |
| `03_queries.sql` | 18 аналитических запросов с комментариями-описаниями |
| `04_extra.sql` | Индексы, представления, процедуры инициализации, транзакции |

### Порядок запуска

1. Создать базу данных в PostgreSQL (например, `carsharing_db`)
2. Выполнить `scripts/01_ddl.sql` — создаст все таблицы. **Порядок важен**: скрипт создаёт таблицы в последовательности, учитывающей внешние ключи (сначала независимые `stations`/`users`, затем зависимые от них)
3. Выполнить `scripts/02_dml.sql` — заполнит таблицы тестовыми данными
4. Выполнить `scripts/03_queries.sql` — можно запускать запросы по одному, каждый снабжён комментарием с описанием цели
5. Выполнить `scripts/04_extra.sql` — создаст индексы и представления, объявит процедуры. **Блоки транзакций внутри этого файла (`BEGIN ... COMMIT`) нужно выполнять целиком, одним пакетом** (например, в DBeaver — выделить весь блок и нажать `Alt+X`), а не построчно — иначе `COMMIT` не найдёт активной транзакции

### Ожидаемые результаты

- После шагов 1–2: 9 пустых таблиц с применёнными ограничениями
- После шага 3: заполненная база — 15 станций, 15 пользователей, 15 транспортных средств, 15 промокодов, 30 версий тарифов (SCD2, 5 тарифов × 6 версий), 40+ поездок, 40+ платежей, 30+ связок с промокодами, 15 записей обслуживания
- После шага 4: каждый запрос возвращает набор строк, соответствующий описанию в комментарии над ним (например, запрос 2 — топ-5 пользователей по бонусам, запрос 18 — календарь ноября с количеством поездок по дням)
- После шага 5: в схеме появляются 5 индексов, 3 представления (`v_trip_details`, `v_current_tariffs`, `v_user_spending`), процедура `add_station`; выполнение блоков транзакций изменяет данные конкретных поездок/платежей/промокодов согласно описанной в комментариях бизнес-логике

### Ограничения

- Данные сгенерированы синтетически для демонстрации структуры и запросов, не являются реальными сведениями о пользователях
- Скрипты рассчитаны на PostgreSQL (используются специфичные для него конструкции: `SERIAL`, `WITH RECURSIVE`, `FOR UPDATE`, оконные функции) — на других СУБД потребуется адаптация синтаксиса
- Скрипт `02_dml.sql` предполагает пустую базу — повторный запуск без предварительной очистки таблиц приведёт к нарушению `UNIQUE`-ограничений

### Где его можно использовать

Схема и подход применимы как основа для:
- Учебного или демонстрационного backend-приложения каршеринга
- Тренировки аналитических SQL-запросов на реалистичном наборе связанных таблиц
- Примера реализации SCD2-версионирования цен/тарифов, применимого не только к каршерингу, но и к любой предметной области с изменяющимися во времени характеристиками (подписки, прайс-листы, условия услуг)
